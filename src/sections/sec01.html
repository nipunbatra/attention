A language model reads the tokens so far and assigns a probability to every possible next token: $$p(x_{t+1}\mid x_1,\ldots,x_t)$$

To predict the next token well, the model needs a useful representation of everything relevant in the preceding context.

$E_{\text{tok}}$ is the learned vocabulary lookup table: one stored row per token.

$t_i$ is the token ID at position $i$. Writing $E_{\text{tok}}[t_i]$ means “read that token’s row from the table.”

The word bank gets the same lookup row wherever it appears.

In a trained model, learning adjusts the table. Here we use hand-chosen rows so we can follow the arithmetic.

In Part I, concatenation kept the positions in separate input slots. Here, we’ll give each token row a position cue before the rows interact.

We add a vector for the token’s position to its vocabulary row. Moving the same word to another slot changes this position cue.

A separate four-coordinate example: the word “the” stays the same. Its position changes.

Still four coordinates. The position cue changes their values without adding another column.

Illustrative word vector. Sinusoidal position vectors. Values rounded to three decimals.

The position cue uses the existing coordinates. It does not add a “pos” column or assign a human meaning to each coordinate. In this example, changing position changes several entries in the row. At position 1, the pattern is $[0,1,0,1]$ because the sine of zero is zero and the cosine of zero is one.

For readers who want the calculation: let pos = i - 1, so the first displayed position has index zero. With four coordinates, the original Transformer’s positional encoding gives p = [sin(pos), cos(pos), sin(pos / 100), cos(pos / 100)]. The pairs vary at different frequencies. The position values here come from that formula, while the word values are chosen just to show the addition.

Positional vectors can also be learned from data. Addition is one way to supply position information, not a requirement for every Transformer architecture. We’ll return to the design choices later.

Write $e_i$ for the current representation at position $i$. Initially, $e_i=e_i^{(0)}$.

$$\ve{E}=\begin{bmatrix}e_1\\e_2\\\vdots\\e_T\end{bmatrix}\in\mathbb{R}^{T\times d_{\text{model}}}$$

$T$ input positions give $T$ rows. Every row still has $d_{\text{model}}$ numbers.

$E_{\text{tok}}$ is stored across sentences. $E$ is built for this sentence; contextual updates change its position rows, not the lookup table.

These are different vectors from the four-coordinate position example. Real learned coordinates need not have such tidy meanings.

The bank toy’s calculations ignore coordinate 5, labelled “pos” in its tables. We’ll use this toy to study which words supply information. The positional-encoding example above shows how a position cue normally spans the vector.

The toy stores an offset in its fifth coordinate, but that coordinate has zero weights in its matching, message, and prediction projections. Its changing predictions therefore demonstrate content gathering, not sensitivity to word order. The named axes and this unused offset are simplifications of the hand-worked example.

The model works with a row of numbers per token. We judge its prediction by the probability it assigns to the correct next word, so those rows need to carry the relevant context.
